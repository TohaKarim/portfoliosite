Library Management System

A system for managing a library's books, members, loans and fines. The focus was a clean relational design and business rules that keep the data correct, even when something goes wrong halfway through an operation.

My roleDeveloper (database design, logic, interface, testing)
StackPython, SQL (SQLite)
TypeDesktop / database application
FocusData integrity & workflow

The problem

Small libraries often track loans on paper or spreadsheets. That leads to double-issued books, lost records and fines calculated by hand. I wanted one system where a librarian can search, issue and return books in seconds, and where the rules are enforced by the software instead of by memory.

My role & responsibilities

What I personally did

  • Gathered requirements and modelled the data as an ER diagram.
  • Created normalised tables with primary keys, foreign keys and constraints.
  • Wrote the issue / return / fine logic inside safe database transactions.
  • Built the search and book-management interface.
  • Tested rule violations (limits, unpaid fines, unavailable books) and fixed edge cases.

Thought process & decisions

From the first idea to the working system, in four steps.

01

Model the data

Get the schema right before any code

I listed the real-world things (books, members, loans, fines) and how they relate. A loan connects one member to one book at a time, and a fine can only exist because of a late loan.

Decision: keep Loans as its own table instead of adding columns to Books, so the full borrowing history is preserved.
02

Design the workflow

Turn rules into steps

Issuing a book is more than inserting a row. The system must check the member's limit, outstanding fines and book availability before it creates the loan, and must calculate a fine on return.

Decision: enforce rules in one service layer, so the interface cannot bypass them.
03

Implementation

Transactions protect the data

Issuing a book changes more than one table. Wrapping the steps in a transaction means either everything succeeds or nothing is saved.

library/service.py
from datetime import date, timedelta

MAX_LOANS = 3
LOAN_DAYS = 14

def issue_book(conn, member_id: int, book_id: int) -> int:
    with conn:                                   # one atomic transaction
        active = conn.execute(
            "SELECT COUNT(*) FROM loans WHERE member_id=? AND returned_on IS NULL",
            (member_id,)).fetchone()[0]
        if active >= MAX_LOANS:
            raise ValueError("Member has reached the loan limit")

        unpaid = conn.execute(
            """SELECT COUNT(*) FROM fines f JOIN loans l ON l.id=f.loan_id
               WHERE l.member_id=? AND f.paid=0""", (member_id,)).fetchone()[0]
        if unpaid:
            raise ValueError("Clear outstanding fines first")

        cur = conn.execute("UPDATE books SET copies = copies - 1 WHERE id=? AND copies > 0", (book_id,))
        if cur.rowcount == 0:
            raise ValueError("No copies available")

        due = date.today() + timedelta(days=LOAN_DAYS)
        cur = conn.execute(
            "INSERT INTO loans(book_id, member_id, issued_on, due_on) VALUES (?,?,?,?)",
            (book_id, member_id, date.today().isoformat(), due.isoformat()))
        return cur.lastrowid
Decision: decrement copies with WHERE copies > 0 inside the same transaction, so two librarians cannot issue the last copy twice.
04

Testing & interface

Try to break it

I tested the rules on purpose: a fourth loan, borrowing with unpaid fines, returning an already returned book, and issuing the last copy. Each one now fails with a clear message instead of corrupting data. Then I built the search and book list you see on the cover image.

The result

4Linked tables with enforced keys
3Business rules checked on every loan
ACIDSafe, all-or-nothing operations
1Source of truth for every loan and fine

What I learned

  • Good schema design prevents entire classes of bugs.
  • Transactions are essential whenever one action touches several tables.
  • Thinking about failure cases first makes software dependable.

Project 01 · Web & API

Real-time Weather App

A weather application built with FastAPI that forecasts real-time weather for any city. It searches the place, fetches live forecast data, validates it and serves clean JSON to a responsive front-end.

My roleDeveloper (design, backend, front-end, testing)
StackPython, FastAPI, httpx, JavaScript
TypeREST API + web client
Data sourceOpen-Meteo forecast API

The problem

Most weather sites are crowded with ads and slow to load. I wanted a fast, focused app that answers one question: "What is the weather like in this city, and what will it be over the next few days?" The goal was also to learn how to design an API that is quick, reliable when the upstream service fails, and easy for a front-end to use.

My role & responsibilities

What I personally did

  • Sketched the interface and defined the API contract before writing any code.
  • Built the FastAPI backend: city search, forecast endpoint, error handling and data models.
  • Added an in-memory cache with a time-to-live to cut upstream calls and response time.
  • Built the responsive JavaScript front-end that renders current conditions and a multi-day forecast.
  • Tested edge cases such as unknown cities, upstream timeouts and unusual characters.

Thought process & decisions

The project moved through four stages. At each one I recorded what I decided and why.

01

Sketch & requirements

Plan the user experience first

I drew a first-draft layout on paper: one search box, a large current temperature, and four forecast cards. Writing down open questions early (caching, units, "city not found") shaped the backend design later.

Decision: keep the UI to a single screen so the API only needs one main endpoint.
02

Architecture

Separate responsibilities

The browser calls my FastAPI backend, never the weather provider directly. The backend checks a cache, calls the geocoding and forecast services when needed, validates the response with Pydantic models and returns tidy JSON.

Decision: use async endpoints with httpx so one slow request does not block others.
03

Implementation

Small, testable pieces

I built geocoding, forecast fetching and caching as separate functions. Here is the core endpoint:

main.py
import time, httpx
from fastapi import FastAPI, HTTPException

app = FastAPI(title="Weather API")
_cache: dict[str, tuple[float, dict]] = {}   # city -> (timestamp, data)
TTL = 600                                    # seconds

async def geocode(client: httpx.AsyncClient, city: str) -> dict:
    r = await client.get("https://geocoding-api.open-meteo.com/v1/search",
                         params={"name": city, "count": 1})
    r.raise_for_status()
    results = r.json().get("results")
    if not results:
        raise HTTPException(404, "City not found")
    return results[0]

@app.get("/weather")
async def weather(city: str):
    key = city.strip().lower()
    hit = _cache.get(key)
    if hit and time.time() - hit[0] < TTL:
        return hit[1]                           # fast path

    try:
        async with httpx.AsyncClient(timeout=10) as client:
            place = await geocode(client, city)
            r = await client.get("https://api.open-meteo.com/v1/forecast", params={
                "latitude": place["latitude"], "longitude": place["longitude"],
                "current_weather": True, "timezone": "auto",
                "daily": "temperature_2m_max,temperature_2m_min,precipitation_sum"})
            r.raise_for_status()
    except httpx.HTTPError:
        raise HTTPException(502, "Weather service unavailable")

    data = {"city": place["name"], "country": place.get("country"),
            "current": r.json()["current_weather"], "daily": r.json()["daily"]}
    _cache[key] = (time.time(), data)
    return data
Decision: return clear status codes (404 for unknown city, 502 for upstream failure) so the UI can show a helpful message.
04

Testing & measuring

Prove that the design choice worked

I compared response times with and without the cache. Repeated searches are served from memory in a few milliseconds, instead of waiting for two network calls.

Decision: a 10-minute TTL balances fresh data with speed, since forecasts do not change every second.

The result

1Focused endpoint, easy for any client to use
~10 minCache lifetime to reduce upstream calls
404 / 502Clear error handling for the UI
AsyncNon-blocking I/O for concurrent users

What I learned

  • Designing the API contract first makes the front-end and back-end easy to build in parallel.
  • External services fail, so timeouts and meaningful error codes are essential.
  • Measuring performance before and after turns an assumption into evidence.

Python Games Collection

Simple but complete games written in Python: Snake, Blocks and a retro console-style platformer. They are small enough to finish, and rich enough to practise algorithms, object-oriented design and clean code.

The idea

Games are a fun way to practise real programming problems: collision detection, state machines, grids, timing and user input. I built three classics to apply the same ideas in different ways and to see how much code can be shared between them.

My role & responsibilities

What I personally did

  • Designed the shared game loop and the structure of each game.
  • Implemented movement, collisions, scoring, levels and game-over logic.
  • Wrote the rendering code, including grids, sprites and the on-screen HUD.
  • Play-tested and tuned speed and difficulty for each game.

Thought process & decisions

01

One loop, three games

Shared architecture

Every game follows the same cycle: read input, update the world, resolve collisions, draw, and wait for the next frame. Writing that loop once let me focus each game on what makes it unique.

Decision: pass a time step (dt) to update() so speed does not depend on the computer's performance.
02

Game 1: Snake

Grids, queues and collisions

The snake is a queue of grid cells: each move adds a new head and removes the tail, unless food was eaten. Collision checks are simple set lookups, which keeps them fast.

snake.py
def step(self):
    head_x, head_y = self.body[0]
    dx, dy = self.direction
    new_head = ((head_x + dx) % COLS, (head_y + dy) % ROWS)   # wrap or die: your choice

    if new_head in self.body_set:                 # O(1) self-collision check
        self.alive = False
        return

    self.body.appendleft(new_head)
    self.body_set.add(new_head)

    if new_head == self.food:
        self.score += 10
        self.food = self.spawn_food()
    else:
        tail = self.body.pop()                    # deque: O(1) at both ends
        self.body_set.discard(tail)
Decision: store the body in a deque plus a set so both moving and collision checks run in constant time.
03

Game 2: Blocks

Matrices, rotation and line clearing

Each piece is a small matrix. Rotating means transposing and reversing rows; before moving I test the new position against the board. When a row is full it is removed and the rows above fall down, which raises the score and level.

Decision: "try the move, undo if invalid" keeps the movement code short and avoids many special cases.
04

Game 3: Retro platformer

Physics and tile collisions

A side-scrolling, console-style game with gravity, jumping, coin collection and tile-based collisions. I separated horizontal and vertical movement so the player slides along walls and lands on platforms correctly.

Decision: resolve X and Y collisions separately; it is a small change that removes most "stuck in the wall" bugs.

What I learned

  • Choosing the right data structure (deque, set, matrix) matters more than clever code.
  • A shared architecture saves time and makes each new game easier to build.
  • Play-testing finds bugs that unit tests never imagine.
